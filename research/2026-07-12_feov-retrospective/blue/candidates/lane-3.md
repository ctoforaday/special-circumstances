### 1.2 The bimodal shape holds, refining H3's boundary

H3 predicted a majority-reproducible-in-simulator class (harness/caller plumbing) against a persistent residual (leaf-node verification, live drift) that "cannot be pulled into the simulator at any complexity cost." **Confirmed, with one refinement the frontier's phrasing missed**: the write-block and `ENAMETOOLONG` defects are not cleanly on either side. They are real, reproducible-in-principle bugs, but the *reproduction environment* is a live Task-tool dispatch or a live Windows shell, not a Node stub of `agent()` — so they are **live-smoke-testable**, a third bucket the frontier's two-way framing (simulator vs. production-only) did not name. This matters for scoping the simulator: it should not attempt to fake Task-tool write-permission semantics or OS command-length limits — that would be complexity spent chasing a boundary the simulator cannot own, exactly the kind of scope creep blue is obliged to resist. The right home for those two is a documented smoke-test checklist (§1.4), not simulator assertions.

### 1.3 The simulator's concrete design

**Shape.** A Node module that `require()`s (or dynamically imports, matching whatever the real harness uses) the exported workflow body, but wraps it so `agent()` and `log()`/`phase()` are injected rather than ambient globals. Two implementation paths, in order of preference:
1. **Best**: refactor `workflow.js` to accept `agent`/`log`/`phase` as parameters (or a single `harness` object) with the real dispatch as the default, so production and test call the identical function with different harnesses. This is a small refactor (the script already treats these as free variables it expects the runtime to inject — turning that into an explicit parameter is a signature change, not new logic).
2. **Fallback if the harness's injection contract is fixed by the Workflow tool itself** (i.e., `agent`, `log`, `phase` are truly ambient and the script cannot be given a parameter): use Node's `vm` module to run the script text in a sandboxed context with fake globals bound to test doubles. Higher complexity, but does not require touching the shipping script's calling convention.

I could not verify from the plugin source alone which of these two the real Workflow tool assumes (the script never declares where `agent`/`log`/`phase`/`args`/`parallel` come from — they read as injected globals) — this is a genuine open question for whoever builds the simulator, not a gap I can resolve from static reading. Flagging it rather than guessing.

**Founding regression suite** (beyond the two the backlog already names — stringified/unbound args, and null-`agent()`-returns) — what else it must contain to be a *founding* suite rather than a token gesture:

1. **Unbound/garbage args** (`args` is the string `"undefined"`, `args` is `{}`, `args.runDir` is `""`, `args.topic` is `undefined`) → assert the script refuses to dispatch any `agent()` call and returns/throws a clear diagnostic naming the bad field. This is run 1, verbatim.
2. **`agent()` resolves `null`** on the red-merge call mid-loop → assert the loop does not throw; assert the run terminates `UNVERIFIED` with whatever partial material exists preserved (this is also backlog item 15(c), "ASSEMBLE-ON-FAILURE" — the null-guard and the never-throw-away-paid-rounds behavior are the same test case, not two).
3. **`agent()` resolves `null`** on the blue-synthesize call, the frontier call, and the final-assembly call — four distinct call sites, four distinct null-handling assertions; the backlog's phrasing ("null-guard every schema'd `agent()` return") implies all of them, but only the red-merge crash was ever actually observed. A regression suite that only guards the one observed site is not founding — it is anecdotal.
4. **Clean PASS on round 1** → assert zero blue-response dispatches, `verdict === 'VERIFIED'`, `rounds === 1`.
5. **Multi-round FAIL → revision → PASS** → assert `blueEnv` is re-dispatched with exactly the open (non-adjudicated) gaps, that `citationPasses` recomputes from the new `claim_count`, and that gap IDs the test fixture marks `closed` in a prior round never reappear in the "open gaps" list passed to blue.
6. **Contested docket → judge → `carried`** → assert the judge is invoked only when `contested.length > 0`; assert `deadlock` stays `false` when a gap is `carried`; assert the carried gap re-enters `openGaps` next round with its `required fix` intact.
7. **Contested docket → judge → `risk_accepted`** → assert the gap is added to `adjudicated` and excluded from the *next* red-merge prompt's gap list (the `${adjudicated.length ? ... : ''}` interpolation branch) — this is the one piece of prompt-construction logic gnarly enough to deserve its own assertion independent of the deadlock check.
8. **Judged deadlock** (no gap carried, no new gaps raised) → assert the loop breaks, `deadlocked === true`, and the final-assembly dispatch receives the deadlock flag in its prompt text.
9. **Safety-ceiling exhaustion** (`maxRounds` reached with red still `FAIL` and no deadlock ruled) → assert `exhausted === true`, `verdict === 'UNVERIFIED'`, and the assembly prompt's ceiling-specific text branch fires (this is exactly what happened in the real run 2 — a live, not hypothetical, case).
10. **`citationPasses` scaling boundary values** — `claim_count` absent (defaults to 20 → 1 pass), `claim_count = 40` (1 pass), `claim_count = 41` (2 passes), `claim_count = 160`+ (caps at 4) → pure arithmetic, asserts the `Math.min(4, Math.max(1, Math.ceil(n/40)))` formula directly, cheap and exhaustive.
11. **Lane-count fidelity** — call with `lanes: 2` and assert exactly 2 `blue-lane-*` dispatches occur, `lanes: 3` (the documented default) dispatches 3. This directly instruments H1's "was lane count under-provisioned" question (§2) — currently the workflow's return object has no `lanes` field at all, so the *only* way to know how many lanes a historical run used is to count files in `blue/candidates/`. Cheap fix, folds into the simulator as an assertion once added.
12. **Friction aggregation** — stub two agents each returning a `friction` array; assert both are namespaced (`"${label}: ${entry}"`) and concatenated into the final return's `friction` field, never dropped or overwritten.
13. **CRLF/line-ending lint** (not an `agent()`-stub case, but belongs in the same CI gate per §1.1) — assert `workflow.js`, the agent `.md` files, and the reference templates are LF-only.

None of these 13 requires a model call, a network call, or a filesystem beyond an in-memory fake — the entire suite should run in well under a second and cost zero tokens, directly answering the backlog's own framing ("Would have caught the run-1 args bug before dispatch [saving] 253k tokens" and "3M tokens of evidence" from run 2's quota crashes).

**What the simulator explicitly does not attempt** (the pragmatist boundary, argued not assumed): Task-tool write-permission semantics, OS-level file/command-length limits, WebFetch/small-model summarization fidelity, live citation re-verification, and any judgment content (whether a rebuttal is *actually* evidence-backed, whether a risk grade is *correctly* assigned) are out of scope by construction — general industry practice on agent-testing draws the same line: mocked-LLM unit tests "catch deterministic code bugs but miss failures in reasoning, hallucination, and context handling that only surface in production," with a commonly cited split of roughly 95% mock-heavy unit tests to 5% real-call integration/end-to-end tests[^AgentTestTiers]. Trying to widen the simulator past this line would be exactly the "design made strictly worse to satisfy an edge case" blue is obliged to resist — a simulator that fakes WebFetch content-lossiness would need an oracle for what the *correct* extraction is, which is the research problem itself, not a test fixture.

## 2. H1 — Lane diversity: confirmed convergent, confirmed under-provisioned, with a corroborated fix

Compared `blue/candidates/lane-1.md` (H1-substrate-first) against `lane-2.md` (H2-consolidation-first) directly, not just via the CHANGELOG's account of them.

- **Structural overlap confirmed.** Both lanes' section lists cover all five original hypotheses (lane-1: H1→H2→H3→[new poisoning risk]→H4→H5; lane-2: H2→[new poisoning risk]→H5→H1→H3→H4) — same five topics, same "breadth after primary" shape the prompt mandates, differing only in ordering.
- **Independent convergence on the same missing risk, confirmed.** Both lanes headline "memory poisoning absent from §9" as their own independent discovery (lane-1 §4: "NEW BLOCKING RISK"; lane-2 §2: "Missing risk (absent from §9 entirely)") — same framing, same section-numbering convention even, arrived at independently per the parallel-dispatch design (lanes cannot see each other's in-flight drafts; `parallel()` dispatches them concurrently).
- **Lane count was under-provisioned, confirmed, and currently unrecoverable except by counting files.** `commands/research.md` documents `--lanes` default 3; only `lane-1.md` and `lane-2.md` exist in run 2's `blue/candidates/` — 2 lanes ran, not 3. Nothing in the workflow's return object, `debate.md`, or `friction.md` records the `lanes` value actually used — the only way I confirmed this was `ls`-ing the candidates directory. This is a real instrumentation gap (H3 §1.3 item 11 already proposes the fix as a simulator assertion once the return object carries the field).
- **Refinement doubts.md and the frontier undersell: convergence on a real, load-bearing gap is a feature, not only waste.** Two independently-dispatched lanes reaching the same finding through different entry hypotheses is textbook independent replication — it raises confidence in the poisoning gap precisely because it was not primed by a shared frontier bullet naming it (the frontier's H1–H5 as reconstructed in `blue/frontier.md` do not mention poisoning at all; both lanes found it as *breadth*, not as their assigned primary). The waste is specifically the *structural* convergence (same section skeleton, same "first hypothesis, then all others" shape, same reliance on `blue/frontier.md` and `references/report_template.md` as the sole shared input driving both toward an identical scaffold) — not the substantive convergence on a real risk. A fix that suppressed convergence indiscriminately would throw away the corroboration signal along with the redundant scaffolding; the fix needs to target the former only.
- **External corroboration for the proposed fix.** Recent work on multi-agent LLM scaling found that ensembles of identically-prompted agents ("homogeneous personas") saturate quickly because outputs correlate, while heterogeneous personas — distinct assigned lenses, not just different starting topics — measurably reduce pairwise error correlation (~19% lower) and recover up to 95% of the gain a fully independent ensemble would achieve[^AgentDiversity]. This directly supports engineering per-lane diversity as *distinct methodological lenses or source-classes* (e.g., lane A: primary literature/benchmarks; lane B: practitioner/production evidence — vendor blogs, postmortems, issue trackers; lane C: adversarial/disconfirming-first, inverting the 1-in-5 floor to a 1-in-2 minimum) rather than merely different starting hypotheses on an identical frontier document, which is what `workflow.js` line 104 currently does verbatim ("lane ${i+1} takes hypothesis ${i+1} first, then breadth" — no lens, no source-class, no method assignment).
- **Disconfirming caveat on the fix.** The same source notes agents sharing a base model and overlapping context remain more correlated than architecturally distinct ensemble members, "making the conditions under which multi-agent diversity actually helps murkier"[^AgentDiversity] — lens-diversity prompting is not a guarantee of independence, only a measured improvement over the status quo. I grade the fix accordingly in §4, not as a solved problem.

## 3. H2 — Consensus vs. minority provenance: confirmed destroyed, not merely under-surfaced

- **Zero provenance tags in the living report.** `grep -c "lane-1\|lane-2"` against `blue/report.md` (2,145 lines) returns nothing. No claim in the living report is marked as originating from one lane, the other, or both.
- **The CHANGELOG has partial, inconsistent attribution language that does not survive synthesis.** Round 0's merge log does use some lane-scoped phrases ("lane 2 unique," "lane-1-specific rows," "lane-1 §5 partial-YAGNI") alongside undifferentiated "union of," "kept both," "merged X + Y" for the majority of items — so the *raw material* for consensus/minority classification briefly existed in the changelog's prose, but nothing carries it forward into `blue/report.md` itself or into red's grading inputs.
- **Red's corroboration grading has no lane-count-agreement channel, confirmed.** `red/findings.md`'s corroboration entries grade citation-support confidence (high/medium/low) per statement↔reference pair; none reference which lane(s) surfaced the claim. The `RED_ENVELOPE` schema in `workflow.js` has no field for it either — there is no channel for this information to travel even if red wanted to grade on it.
- **This is the doubt exactly as doubts.md states it**, not a milder "under-surfaced" version: the union-merge operation is lossy by construction for this one dimension, even though it is scrupulously non-lossy for content (verified: no substantive claim from either lane is missing from the final report — the CHANGELOG's dedup accounting is honest and traceable).
- **A concrete, already-proposed fix exists and is externally well-precedented.** `ideas/backlog.md` item (5) proposes a **claim manifest**: blue emits a machine-readable ledger (claim → citation → self-graded confidence → lane provenance) alongside the prose report. This is not a novel idea invented for this retrospective — "evidence tracing" and "execution provenance" for LLM-agent claims is an active, named research area (e.g., a 2026 survey formalizing "execution provenance" as a typed graph of agent activity and "evidence tracing" as its projection onto evidence-support relations, and `PROV-AGENT`, which extends the W3C PROV data model with LLM-specific entities for exactly this kind of claim-to-source-to-agent lineage)[^ProvenanceSurvey]. The backlog's claim manifest is a lightweight, single-file instance of the same idea, sized to this system rather than a general framework — appropriately cheap.
- **Grading the fix**: high likelihood of resolving the doubt (it directly answers "can the report tell which claims all lanes agreed on") × medium-high impact (feeds red's corroboration grading, feeds future self-improvement passes, and is the same artifact the backlog independently proposes for cutting red's reading cost — "red walks the manifest instead of parsing 53KB of prose") × low-medium complexity (one more structured field blue already produces internally when synthesizing by dedup — the information exists transiently during the merge and is currently discarded, not absent).

## 6. H5's parenthetical is disconfirmed; the ranking's shape is confirmed

H5 predicted the write-block/`ENAMETOOLONG`/preflight-guard cluster is "round 1 only (**already fixed**)." The clustering-in-round-1 half is correct; **"already fixed" is false for all three items in the cluster**: the write-block is an open, unchecked `ideas/backlog.md` item (§4 row 5/6 above); `ENAMETOOLONG` has no proposed or landed fix beyond the ad hoc chunking workaround the agent improvised in the moment; and the preflight guard — per §0 — was never actually written despite `run1-friction.md`'s own text claiming it had been. H5 is therefore **confirmed on the shape (top-2 items are the stable, multi-role, multi-round ones; everything else is a short tail) and refuted on the parenthetical** — which is itself evidence for the report's overarching finding that backlog/friction self-reporting about remediation status cannot be trusted without a source check (§0), and one more argument for the simulator: a regression suite is the only mechanism in this system that cannot be fooled by an inaccurate status line in a markdown file.

## 7. Breadth beyond H1–H5: the doubts the frontier did not formalize as hypotheses

`doubts.md` lists three additional open items the retrospective's own frontier (`blue/frontier.md`) never converted into H1–H5 — worth checking directly against run 2's `report.md` since they bear on the same "what should the report/template look like before run 4" question as H4.

- **"Duplication between the meat and blue-in-full" — checked against `report.md`, appears refuted for this run.** The assembled report's top-level `## Analysis` section (`report.md` lines 34–42) is a genuinely distinct, higher-order synthesis — it makes build-vs-adopt argumentative moves, cites specific blue sub-section numbers by reference, and states a verdict-rationale that does not appear verbatim anywhere in `blue/report.md`. It is not a compressed digest of blue's report and it is not a copy-paste. This doubt is **not confirmed** by the one data point available; it may still be a risk on a topic where the analytical core has less independent argument to make than a build-vs-adopt architecture decision does, but nothing in the corpus demonstrates the duplication doubts.md worried about.
- **"Blue's `open_questions` have no home in the report template" — confirmed.** `blueEnv`'s schema requires `open_questions` (a non-empty-by-schema array in every blue envelope); `report.md` (2,970 lines total) contains zero occurrences of the string "open question" anywhere, including inside the embedded blue-report-in-full and red-findings-in-full sections. The field is faithfully populated by blue every round (I did not check every intermediate envelope, but the schema requires it) and then silently dropped at final assembly — `references/report_template.md` has no section for it. **Confirmed exactly as doubts.md states, and unresolved by H1–H5** since no frontier hypothesis tested it. Cheap fix: add an "Open questions carried past this run" subsection to the report template, sourced from the last blue envelope's `open_questions` field (which the workflow script already has in scope as `blueEnv.open_questions` at assembly time — it is simply never passed into the assembly prompt).
- **"The Heilmeier is DARPA-shaped" / "the risk matrix presumes a design under evaluation" — not usefully tested by either run.** Run 1 never reached a real topic (harness defect only). Run 2's topic (a build/architecture decision for a proposed memory system) is close to Heilmeier's native shape (cost, timeline, milestones map naturally onto phased implementation effort) — and indeed the catechism in `report.md` §Heilmeier reads coherently, not strained. This is **weak, single-instance disconfirming evidence** against the doubt for build-decision topics specifically, but the doubt was framed against "explainer or survey" topics, which neither run has yet been. **Needs instrumentation**: run this engine once on a genuinely explanatory/survey-shaped topic (no build decision, no cost/schedule axis) before drawing a conclusion either way — the doubt is neither confirmed nor refuted by the corpus available, only untested in its actual target case.

## 8. An unlisted positive finding: the red-auditor project-memory loop is real and working

Not a doubt in `doubts.md` and not one of H1–H5, but additive and directly relevant to both H3 (what needs testing) and H4 (what's already working and shouldn't be touched): `agents/red-auditor.md` mandates *"AFTER catching a new gap pattern (not instance), YOU MUST record it in your project memory."* I found the actual memory store outside the research corpus, at `AgentOrange/.claude/agent-memory/frank-exchange-of-views-red-auditor/` (a different project root than the retrospective's own `special-circumstances` — the plugin evidently ran its live debates against the `AgentOrange` project, not the one holding this retrospective's files; worth noting as a path-provenance detail for anyone trying to reproduce this check). It holds **15 distinct, well-formed gap-pattern files** (`workflow_undefined_rundir.md`, `pattern_self_defeating_mitigation.md`, `pattern_invariant_soundness_by_enumeration.md`, `pattern_policy_without_mechanism.md`, and eleven more), each a generalized lesson abstracted from a specific run-2 gap (e.g., `pattern_invariant_soundness_by_enumeration.md` generalizes R4-1's denylist-vs-allowlist finding into a reusable audit heuristic: "prove incompleteness via the system's own symmetric defense; recommend allowlist inversion"). This confirms the self-improvement mechanism the design intends for red is **functioning as specified, not aspirational** — a genuine positive finding to weigh against the defect-heavy material above. It also surfaces a real **asymmetry**: only `red-auditor.md` declares `memory: project`; `blue-researcher.md` and `lead-judge.md` do not, so blue never accumulates its own cross-run learning and — per `ideas/backlog.md` item 4 — is not even instructed to *read* red's accumulated library before submitting, despite the mechanism existing and being populated (H4 row 10 addresses this directly).
