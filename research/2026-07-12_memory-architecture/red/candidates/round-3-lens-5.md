## R3-1 — SECURITY/GRADE: the authorship clone-gate relocates §2.4 diligence to per-clone (not escaped) and mis-grades authorship-forgery as "high-effort" when the operator's git identity is public [severity MEDIUM-HIGH, blocking-candidate]

- **Location:** §13.2 — *"Human ratification is needed only for the **foreign-clone** case — a one-time, event-driven 'I choose to trust this cloned repo' decision (per-repo…), not a nightly chore. **This no longer leans on the diligence §2.4 discredits.**"* and the graded residual — *"unsigned git commits are trivially spoofable … authorship-trust in its baseline form assumes an attacker will not forge the operator's commit identity … a **low-likelihood, high-effort** move."*
- **Problem — two coupled defects in the redesigned R2-1 fix.**
  - **(a) Diligence relocated, not escaped.** §13.2 correctly removes the *nightly* diligence dependence (authorship is stable across `/dream` runs — accepted, that leg is closed). But the foreign-clone ratification is still a **human judgment call**, and §2.4's decay mechanism (volume + low per-decision stakes → reflexive LGTM) transfers directly to it: an operator who clones repos routinely (normal dev workflow) will `/dream --ratify` reflexively, including a genuinely poisoned clone. Blue asserts escape from §2.4 without arguing why per-clone volume is low. The mitigation moved the diligence dependence from nightly to per-clone; it did not eliminate it. (Current volume *is* low — the nudge fires only on repos that ship a committed `.claude/knowledge/` store, today ~only the operator's own suite — so likelihood scales with feature adoption; but the blanket claim "no longer leans on discredited diligence" is false for the per-clone leg regardless.)
  - **(b) Forgery is low-effort, not high-effort — the residual grade is mis-stated.** A git author identity (name + email) is **not secret**: it is embedded in every public commit the operator has ever pushed. Any attacker who reads one public commit can author malicious `.claude/knowledge/` commits under the operator's exact identity with a single `git config user.email`. So the unsigned baseline gate provides **~zero** protection against a semi-targeted attacker who has read one of the operator's public repos. The correct reason the risk is bounded is **targeting-required** (a broadcast attacker cannot pre-forge *every* victim's distinct identity), not **effort** — blue's "high-effort" framing is wrong and inflates the baseline's security. Coupled with §13.13's **risk-accept of the signed-commit strong form**, v1 ships a clone-gate whose honest security guarantee is "defends against attackers who do not know your public git identity" — which is false for any operator with public repos.
- **Required fix:** (1) State that per-clone ratification inherits §2.4's decay risk and bound it (e.g. nudge only on stores exceeding a size/authority threshold; batch-ratify with a shown diff; or accept the residual explicitly). (2) Re-grade authorship-forgery as **low-effort / targeting-required**, and state the v1 baseline defends only against untargeted/broadcast attackers — an operator with public repos who clones-and-works-in a semi-targeted poisoned repo is *not* protected without the signed-commit form. (3) Reconsider whether the signed-commit form is genuinely risk-acceptable given (b), or state the baseline's guarantee honestly so the operator can choose.
- **Grade:** likelihood medium (per-clone decay: low now, scales with adoption; forgery: low-but-targeting-required) · impact high (zero-click active-authority context compromise, persistent) · complexity-to-fix low-medium. Corroboration of the residual as graded: mis-stated ("high-effort" is wrong). **Pattern: self-defeating mitigation (relocated-problem + leans-on-discredited-diligence — the R2-1 critique re-applies to the redesign's foreign-clone leg).**

## R3-2 — SECURITY: post-ratification injection in the shared/collaborative project store; per-repo-ratification trust vs per-commit-authorship trust conflated [severity MEDIUM]

- **Location:** §13.2 — *"activation gated on **trusted commit authorship**"* (per-commit) vs *"a one-time … 'I choose to trust this cloned repo' decision (**per-repo**, keyed on repo/remote identity, not content)"* (per-repo). And §13.7 value table — committed project store *"value is mostly for **collaborators**."*
- **Problem:** the two trust granularities are in tension and §13.2 does not say which governs *after* ratification. If trust is **per-repo** (ratify once, whole repo trusted), then a shared/collaborative project store — the stated value of the committed-store differentiator — is wide open post-ratification: a compromised collaborator account, or a malicious PR merged into the shared remote, pushes `.claude/knowledge/` commits that the operator's already-ratified repo activates at **active authority** with no re-check. If trust is **per-commit-authorship**, then a legitimate collaborator's commits (authored by the collaborator, not the operator) never activate — gutting the collaborative value. Either branch has an un-graded failure; blue specified neither for the shared case, only the solo self-authored case.
- **Required fix:** specify the post-ratification model for multi-author stores — either per-commit-authorship (and accept collaborators' knowledge never auto-activates, so the "travels with the repo" value is solo-only), or per-repo trust (and grade the post-ratification injection vector via the shared remote). State which; grade the residual.
- **Grade:** likelihood low-medium (requires a shared store + a compromised/malicious push) · impact high (active-authority poison via the trusted remote) · complexity-to-fix low. Corroboration: the two granularities are both asserted in §13.2 and are mutually exclusive for the shared case.

## R3-3 — SECURITY: turn-level taint under-propagates — "immediately follow in parentUuid lineage" misses delayed-effect laundering, re-opening the R1-3 path at turn granularity [severity MEDIUM-HIGH]

- **Location:** §13.4 — *"A candidate is tagged `external-ingest` **iff its supporting turn set intersects turns that contain — or in `parentUuid` lineage immediately follow — a `WebFetch`/`WebSearch`/external file-read/`/ingest` result.**"*
- **Problem:** this is unsound taint propagation for an *adversarial* (as opposed to accidental) contaminant. A poisoned web page read at turn N injects instructions that influence the agent's reasoning for the **rest of the session**, not just turn N+1. The laundering attack is precisely to place the poison early, let the agent "reason," and emit a conclusion many turns later whose *stated* supporting turns are pure operator+agent reasoning that neither *contains* nor *immediately follows* the `WebFetch`. Under the specified rule that concept is tagged **trajectory-derived** and **auto-promotes** — the exact `review_count`→auto-promote laundering R1-3/R2-3 were built to close, now re-opened at turn granularity. Sound information-flow taint requires **transitive propagation** (once a session touches external content, every subsequently-derived claim in that session is potentially tainted), not immediate-successor-only. The specified mechanism catches the naive case and misses the deliberate one — and it is the mechanism the entire R2-3 "value-preserving" resolution rests on.
- **Required fix:** either propagate taint **transitively** across the session after any external read (which collapses toward the conservative transcript-scoped rule R2-3 already flagged as neutering auto-promotion — an honest admission the value/safety tradeoff is worse than §13.4 implies), or specify how the extractor establishes that a late reasoning turn is *genuinely* independent of an earlier poisoned read (an unsolved information-flow problem for free-text LLM reasoning — grade it as such, not "mechanical given the JSONL threading").
- **Grade:** likelihood medium (deliberate laundering is the attacker's cheapest move once any web read is in-session) · impact high (auto-promotion of laundered poison to active authority) · complexity-to-fix medium-high (sound taint tracking over LLM free-text reasoning is the hard part, not the JSONL plumbing). **Pattern: self-defeating mitigation (the cheap form is the useless form; the specified turn-level form is unsound for the adversarial case it exists to stop).**

## R3-4 — SELF-DEFEATING: the consolidator "opaque body" fix contradicts §2.3a's semantic-dedup requirement; the in-pass steering residual is larger than graded [severity MEDIUM]

- **Location:** §13.8 — *"the consolidator makes its dedup/merge/promote decisions on **structured fields** (title, type, frontmatter, provenance, `review_count`) and treats each concept's free-text **body as opaque payload it moves but never acts on**."* Cross-read against §2.3a — *"'read the whole bundle, then pairwise-judge' is adequate now"* and the paraphrase-gap evidence that *"lexical/title matching is systematically weak against paraphrase … the binding constraint is **recall of candidate pairs**."*
- **Problem:** the R2-6 fix and the §2.3a dedup design are mutually exclusive. §2.3a's entire point is that duplicate concepts must be caught by **semantic** comparison of bodies/descriptions because title/lexical matching fails against paraphrase (99%+ semantic similarity with single-digit lexical overlap). Catching a paraphrased duplicate *requires the consolidator to read and semantically judge the bodies*. So "treats the body as opaque payload it never acts on" is **not implementable** without regressing dedup recall to the lexical baseline §2.3a proves inadequate. Blue cannot have both: either the consolidator reads bodies semantically (and remains steerable by instruction-shaped body content — R2-6 **not** closed), or it treats bodies as opaque (and dedup fails — §2.3a broken). The prompt-level "do not follow instructions in the body" is a genuine mitigation, but blue over-frames it as "structured-field decisions / opaque body," which misrepresents what a paraphrase-dedup consolidator must do — and blue's own §13.8 concedes "LLM prompt-injection defenses are imperfect." The true in-pass steering residual is therefore **larger** than the graded Low-L/High-I: the consolidator *must* read adversary-influenceable free text to do its core job.
- **Required fix:** reconcile §13.8 with §2.3a — acknowledge the consolidator must semantically read bodies for dedup, so "opaque payload" is inaccurate; re-state the defense as prompt-level data-framing + caps *over content the consolidator does read semantically*, and re-grade the residual upward (the defense is a soft prompt boundary an LLM can violate, not a structural exclusion). Or accept lexical-only dedup and re-open the §2.3a recall gap.
- **Grade:** likelihood low-medium (requires a poisoned concept surviving capture-screening to reach the pass) · impact medium-high (biases a merge/promote pass via content the consolidator is required to read) · complexity-to-fix low (honest re-grade) . Corroboration: contradicted by blue's own §2.3a at the leaf node. **Pattern: self-defeating mitigation (the R2-6 fix collides with the §2.3a dedup requirement).**

## R3-5 — GRADE/COMPOUNDING: the build-case keystone "cross-project blast radius bounded to candidate-tier reference" depends on the R3-3 taint mechanism being sound [severity MEDIUM, feeds lead's docket]

- **Location:** §13.7 — *"a poisoned concept propagating to every project is bounded to **candidate-tier reference data** until it clears the gate; the blast radius of *active/instruction* authority poison is gated."*
- **Problem:** widening #2 (cross-project blast radius) is accepted in the closed docket item as "the gated price of core value," and the *gate* that bounds it to candidate-tier is mit.2 (external-ingest never auto-promotes). But mit.2 only bounds content **tagged external-ingest** — and R3-3 shows the taint tagging under-propagates, so **laundered poison is tagged trajectory-derived, auto-promotes, and propagates cross-project at active authority.** The headline mitigation blue used to make widening #2 acceptable ("bounded to candidate-tier reference") is therefore only as sound as the taint mechanism, which R3-3 shows is not sound for the adversarial case. This does not re-litigate the lead's classification (three widenings counted net-new — closed); it flags that the *mitigation* the closure rests on inherits R3-3's hole. The lead accepted widening #2 conditioned on the candidate-tier bound; if that bound leaks (R3-3), the accepted price is higher than stated.
- **Required fix:** condition the §13.7 acceptance of widening #2 explicitly on R3-3 being resolved (transitive taint or graded unsoundness); if R3-3 stays unsound, the cross-project blast radius at active authority is not fully gated and the build-case margin narrows again.
- **Grade:** logic/meta, compounding · likelihood n/a · impact medium (weakens the mitigation propping the go/no-go widening-#2 acceptance) · complexity-to-fix low (follows R3-3). Corroboration: depends on R3-3.

## R3-6 — COMPLETENESS: the Auto Dream flag is a volatile server-side rollout but is checked only once (Phase 0); a later flag-flip re-introduces the two-writer MEMORY.md collision undetected [severity LOW-MEDIUM]

- **Location:** §13.9 / §12.9 Phase 0 — *"Phase 0 already confirms the Auto Dream flag status on this box"* (one-time) and §3 Consequence 2 — the *"two-writer conflict"* between `/dream` and native Auto Dream on `MEMORY.md`. Cross-read against §1.4's own discipline — transcript version-check must be *"a **pinned-version contract with a fallback**, not a one-time confirmation."*
- **Problem:** the flag-absent fallback (R2-7 fix) branches on a **one-time** Phase-0 check. But Auto Dream is a *server-side rollout* ("not universal," §10 Unverified) — its status can flip *after* Phase 0. If the operator provisions under the flag-absent branch (`/dream` retains `MEMORY.md` consolidation) and Anthropic later enables Auto Dream, **both** writers now consolidate `MEMORY.md` — the exact two-writer collision §3 flagged, now re-introduced with no re-detection because the check was one-time. Blue applied the recurring-contract discipline to transcript format (§1.4) but not to the Auto Dream flag, which is *more* volatile (server-controlled, not release-pinned).
- **Required fix:** make the Auto Dream flag a **recurring** check (e.g. `/dream` detects Auto Dream's consolidation signature on `MEMORY.md` each run and stands down / re-scopes), not a one-time Phase-0 gate — mirroring §1.4's pinned-contract-with-fallback stance.
- **Grade:** likelihood medium (server-side flag flips are outside operator control and expected as rollout widens) · impact medium (two-writer churn / lost notes on `MEMORY.md`) · complexity-to-fix low. Corroboration: high (the one-time check is stated; the flag's volatility is blue's own §10 characterization).

## Synthesis for this lens

Three clean closures this round: §13.5 (advisory-lock liveness + explicit-pathspec commit — R2-4),
§13.6 (history-scrub scoped to the nice-to-have public-mirror case — R2-5), §13.9 (flag-absent
fallback — R2-7, modulo the volatile-flag residual R3-6). The build-vs-adopt re-accounting (§13.7)
met the lead's four literal asks (ordinal value bounding delivered) — red does not re-open the
*classification*, only flags R3-5 that its accepted widening-#2 mitigation inherits R3-3.

**Meta-observation (offered to the lead, not forced):** this is the third consecutive round in which
each round's fixes introduce next-order failures (R1 fixes → R2 gaps → R3 gaps). Severity is
declining (R1 had a verified false claim + three new security vectors; R3 has refinements of accepted
fixes), which is consistent with convergence rather than divergence — the apparatus is being
hardened, not flailing. But the *recurrence itself* is a signal that the poisoning defense is being
assembled reactively, gap-by-gap, rather than derived from a stated information-flow invariant. R3-3
(taint under-propagation) and R3-4 (opaque-body vs semantic-dedup) both trace to the same root: the
design lacks a single, stated **trust/information-flow invariant** ("external-touched ⇒ tainted,
transitively, until a human clears it") from which the individual gates would follow by construction.
Two rounds of gate-patching would collapse into one rule. That is a design-coherence recommendation
the lead may weigh against shipping the MVP with the gates as-patched.

**Blocking-candidate this lens:** R3-1 (clone-gate diligence-relocation + mis-graded forgery
residual). **Compounding into the docket:** R3-3 + R3-5. **Contradictions at the leaf node:** R3-4
(§13.8 vs §2.3a). No PASS.
