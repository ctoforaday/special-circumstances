## The Catechism

**1. What are we trying to do?**
Ship the first real increment of an autonomous self-improvement loop: a scheduled or manually-triggered process that reads the project's own friction, run records, telemetry, and prior rulings; picks one thing to improve; runs it through the existing deep-research debate machinery; and stops at a human gate before anything it produces becomes a standing rule the rest of the system trusts.

**2. How is it handled today, and what does that cost us?**
Today it is not handled at all in a running sense: the sleeper-service plugin carries exactly three files — `plugin.json`, `README.md`, `bin/.gitkeep` — and its own README says so ("Status: scaffold only (Phase 0)"). Every other piece described in the plan (`self-improve.md`, `graduate.md`, the `continuous-learning` skill, `docs/scheduling.md`) is absent from the tree at the pinned commit. The cost of "today" is that all self-improvement is manual: a human notices friction, decides it matters, and starts research by hand. That is slow and it does not scale with the number of runs the system now produces, but it is also the only mode that has ever been exercised, and it is not unsafe by construction the way an unattended loop can be.

**3. What is new here, and why do we believe it works?**
What is new is not a novel algorithm — it is closing the loop: wiring the deep-research debate engine (already built and load-bearing for this very report) to run on inputs the system produces about itself, gated by a human before any output becomes durable. We believe the *debate mechanism* works because it is what produced this report. We do NOT yet have evidence the *loop* works, because the loop itself has not been built. The belief that closing it is worthwhile rests on: (a) the accumulate-don't-replace shape of `research/`+`ideas/` is on the literature's safe side of the self-referential-data-loop hazard (generated data accumulating beside real data avoids the collapse that occurs when it replaces real data); (b) the repo already has a working human-gated promotion pattern (the `motion`/`law/proposed/` ruling flow) that the loop can reuse rather than invent; (c) the friction and telemetry the loop would consume already exist as mediated records, not as something that would need to be built from scratch.

**4. The case against — every honest reason not to do this, at full strength.**
- *The subject does not exist.* There is nothing to ship in the sense of "merge a working loop" — the honest verification state is not-tested-because-absent, not tested-and-passing, and no amount of sound design argument changes that. A report that recommends conditions for shipping something unbuilt is, at best, a spec for the next PRs, not evidence the increment works.
- *The core safety guarantee is currently prose.* The single claim that makes an unattended, scheduled, headless loop tolerable — "it writes only `research/` and `ideas/`" — has no enforcing mechanism anywhere in the suite today. The Phase-4 "verify" step is a one-run observation, not a gate; a happy-path pass on one execution says nothing about the next thousand. Even after Issue C (a `PreToolUse` confinement hook) ships, it is new, untested-in-production machinery, and new hooks have their own failure modes (this very run demonstrated a hook silently failing to fire — the record-tool's identity-binding PreToolUse hook did not reach this seat, and every seat in the run was affected). A confinement hook that can itself fail silently is a residual risk this report does not resolve, only names.
- *The topic-selection criterion this report recommends is deliberately the cheap version, not the sound one.* A one-line priority rule (frequency × blast-radius ÷ fix-cost) is recommended in preference to a bandit/active-learning controller specifically to avoid over-scoping increment 1 — but the literature's own argument (Q2) is that unguided or weakly-guided selection pays a compounding cost over repeated cycles. Shipping the cheap version accepts that compounding cost as the price of not gold-plating a first increment; it is a real, stated risk-acceptance, not a solved problem.
- *The MEMORY-rung corroboration bar (≥2 independent trajectories) is a heuristic, not a proof, and the repo's own ruling says why it can fail.* `priors-are-poison.md` names three mechanisms — Goodhart, cross-topic confound, salience — by which cross-run priors mislead, and this very run's constitution notes that gap-pattern warnings were read and their exact failure modes committed anyway in prior sittings. A corroboration count of 2 does not distinguish two *independent* failures of the same underlying cause from two *repetitions* of one shallow error; nothing in this report's recommendation closes that gap, it only raises the bar from "1" to "2," which is better, not sufficient.
- *Cadence deferred to manual removes the queueing risk by removing the automation, which is close to removing the thing being shipped.* If increment 1 ships with no schedule at all, the "self-improvement loop" is, for a while, indistinguishable from "a human runs `/self-improve` by hand," which is barely more automated than the status quo it is meant to improve on. That is the correct order of operations (get the gate right before the tap is left open) but it means the near-term value of increment 1 is smaller than "autonomous self-improvement" promises.
- *Two different promotion ladders are named in the corpus and this report does not resolve which one governs.* `claude-port-plan.md` §3c states insight → MEMORY → rule-skill → cheatsheet; `memory-architecture.md`, which explicitly supersedes the port plan's ad-hoc memory position, states a five-stage ladder with automated promotion at `review_count ≥ 2`. Shipping without resolving this leaves an open question about which document a builder should follow, and the two are not drop-in compatible.
- *Every acceptance criterion in this report is proposed, not observed.* The operator's binding standing requirement is prototyping and testing as verification, and this report supplies acceptance criteria, not results. That is a real complexity and honesty cost this report accepts rather than resolves: the reader should not leave believing the loop has been prototyped and tested, only that a testable spec now exists for the PRs that would do so.

**5. Of interest, or merely interesting?**
Of interest. The friction and run-record corpus this loop would consume is real, growing, and currently read only by hand; the promotion gate pattern is already proven by the `motion`/`law` flow; and the plugin already occupies a marketplace slot with nothing behind it, which is a worse state than either shipping the conditions above or withdrawing. What it would displace is a small amount of maintainer attention on writing four straightforward artifacts (a command, a skill stub, a scheduling doc, a confinement hook) — cheap relative to the value of turning the corpus this repo already produces into tracked, human-reviewable improvement proposals instead of accumulating unread.

**6. What changes if it works, and what happens if we simply don't do it?**
If it works: friction and research debt that currently only a human notices gets surfaced, ranked, and turned into reviewable tracked issues on a cadence the human actually controls, without anyone having to remember to look. If we don't do it: the corpus keeps accumulating exactly as it does today — silently, in a gitignored `research/` directory that does not even survive a container recycle except through `run-archive/` — and the marketplace continues to advertise a plugin that does nothing. Nothing catastrophic happens either way in the short term; the cost of not doing it is opportunity cost, stated plainly, and the cost of doing it wrong (per the case against) is a loop that runs unattended with a prose-only blast-radius guarantee.

**7. What does it cost, and where would we stop?**
The cost, scoped to the six tracked issues this report recommends — five convergent findings plus manifest honesty as a folded-in single-lane correction — (manual `/self-improve`, record-mediated friction input, a mechanized confinement hook, a written selection rule, cadence deferred to manual, and manifest honesty), is a handful of small, independently-acceptance-tested PRs — not a research programme. The stopping points are explicit in the recommendations themselves: do not build a bandit controller before a reward signal exists from real cycles; do not enable any schedule before the confinement hook is green; do not resolve the two-ladder question by picking one silently — surface it as its own decision. If the confinement hook cannot be made to fail closed (rather than silently disarm, as this run's own hook did), that is the point at which withdrawal, not a patched-over ship, is the honest call.

**Topic selection: an unspecified criterion sitting on top of a demonstrably non-neutral picker.** The plan's only description of topic choice is "enumerate own rules/skills/agents/ideas/research → pick one → `/research`" (§3c) plus "consumes the friction records... as a first-class input" (§4). No criterion maps any input to an ordering over candidates; `grep`-ing the plan text for priority/rank/score terms returns nothing, and the one place a criterion could plausibly live — a `continuous-learning` skill — does not exist in the tree. [minority: lane-2] A substantial body of primary literature bears on why an unstated criterion is not a neutral default: active learning's entire premise is that arbitrary/random selection from a candidate pool is the baseline that principled query strategies (uncertainty sampling, expected error reduction) are built to beat[^1]; multi-armed bandit theory shows that repeated selection under uncertainty with no explore/exploit accounting has no regret guarantee and the cost compounds with the number of cycles[^2] (the cited analysis defines cumulative regret and invokes the classical Lai-Robbins lower bound, establishing that no selection policy escapes a nonzero regret floor accumulating over repeated draws under uncertainty; the sharper UCB1 logarithmic-regret result belongs to a separate bandit analysis and is not claimed from these cached bytes); and "Lost in the Middle[^3]" demonstrates a measured U-shaped positional bias in how language models locate and use items from a list, which — while measured for retrieval/QA, not candidate selection, and therefore transferred here only as inference — is a concrete reason to doubt that "enumerate then pick" samples the candidate space uniformly rather than by where an item happens to sit in the enumeration. [minority: lane-2] The literature also supplies a fitting off-the-shelf criterion rather than requiring one to be invented: Weighted Shortest Job First (Cost of Delay ÷ job size) is the standard sequencing rule for exactly this shape of problem[^4] — a backlog of candidate improvements competing for a scarce reviewer's attention — and maps directly onto friction-frequency × blast-radius as Cost of Delay and estimated fix-cost as job size. Two lanes independently proposed materially the same minimal rule without reference to WSJF (recurrence × blast-radius ÷ fix-cost, tie-broken by oldest-unaddressed), which the literature retroactively grounds. [minority: lane-1] Raw friction *frequency*, however, is itself an unsafe scoring input if a single recurring infrastructure cause (this run's own hook-registration failure, which recurred across the run and would recur on every future headless cycle under the current design) is allowed to dominate a frequency count; the fix is to score distinct causes with de-duplication or decay, not raw event counts.

**Cadence: two independent models of the same conclusion.** The plan resolves cadence to "daily default... over the old hourly, manual run always available, scheduling always human-opt-in" (Resolved decision 6) — but this exists only as prose; `docs/scheduling.md`, where the actual recipes (manual, Task Scheduler + `claude -p`, cloud agent) would live, does not exist. Two lanes modeled the consequence of the daily default independently and arrived at compatible but distinct results, both computed and recorded as re-runnable scripts. The first models the promotion-into-rules/skills gate as a single-server queue: arrivals λ from daily runs, service μ from a single maintainer's promotion throughput, ρ = λ/μ. Little's Law — a distribution-free conservation identity (L=λW) presupposing only a finite mean wait — supplies the no-assumption-about-arrivals property alone[^5]; the instability itself (backlog growing without bound once ρ ≥ 1) is a separate utilization/stability result, λ < μ for a stable single server, which the M/M/1 computation below exercises directly rather than deriving it from Little's Law; the computed frontier is that a maintainer clearing μ promotions/week is stable at daily cadence only if the fraction of runs yielding a promotable candidate stays below μ/7 (μ=3/wk → below ~43%), and the M/M/1 illustration of backlog and wait time shows the degradation is a hockey stick near ρ=1 — the specific week-counts are an explicitly illustrative bound on the *shape* of the divergence, not a prediction of its magnitude, resting on a Poisson/exponential idealization a calendar-timed cadence violates (declined line of inquiry Q8 flagged exactly that premise; its record is amended this round to acknowledge the illustrative Wq bound was wanted after all, superseding Q8's earlier "over-precision" framing): illustrative backlog/wait estimates ~14 items/~5 weeks at ρ=0.93, rising to ~749 items/~250 weeks at ρ≈0.999[^P2] (that pair is exactly ρ=749/750, which rounds to 1.00 only at two decimals — it sits just below the divergence, not at it; "ρ=1.00"/"ρ≥1" is reserved for the unbounded-backlog statement above, where an M/M/1 queue is null-recurrent and both L and W are infinite) under the model's Poisson/exponential idealization[^P3] rather than a gentle ramp — both the divergence at ρ≥1 and the *qualitative shape* of the superlinear approach to it are robust to the specific distributional assumption — Kingman's G/G/1 approximation preserves the same ρ/(1−ρ) hyperbolic divergence and its ρ=1 location for any nonzero total variability (Ca²+Cs²). The specific illustrative *magnitudes* quoted above are not themselves assumption-free: they are M/M/1 values (Ca²=Cs²=1), and under calendar-timed arrivals (Ca²→0) with exponential-scale service (Cs²=1) Kingman's (Ca²+Cs²)/2 factor falls from 1 to ½ — exactly halving every illustrative wait at matched ρ[^P4], a constant rescaling of the same curve, not a change in its shape or its ρ=1 divergence point. The second model observes that the gated resource is only the *promotion*, not the antecedent writes: `research/`+`ideas/` writes are ungated and already accumulate (measured, re-run at synthesis time, at 30 files / ~508KB across both directories[^P5] — a figure that grew from the 28 files / ~448KB an earlier lane measured, because the count includes this very run's own in-progress research directory and is not stable while the run is live; `ideas/` alone holds 4 substantive files plus a `.gitkeep`, itself falsifying a reading of the plugin as producing only empty scaffolding), so the diverging cost under daily cadence is not a blocked queue's wait time but an unbounded *candidate pool* the human must search over before picking what to promote, which routes the cadence risk directly into the topic-selection problem above. Both models agree on the resolution — pace arrivals by the bottleneck (a pull/threshold trigger on unreviewed-corpus depth, or gating the schedule behind "promotion queue not full"), not an unconditional calendar cron — and both honor the same disconfirming path: since scheduling is opt-in and manual is always available, a human who only ever enables the schedule when they have review capacity never lets the queue or pool diverge, which weakens the finding from "the loop is unstable" to "the *documented default* invites an operator to leave an unstable configuration running," a weaker but still real and still-fixed-the-same-way claim. Issue #429's own chosen "ship" exit describes a manual `/self-improve` with no cron, which the leaf evidence independently agrees is the right first-increment default. A safety cross-term the value framing hides: an *enabled* automated cadence held near the ρ=1 divergence does not merely delay promotions — it drives the reviewer's backlog into the hockey-stick regime above, and a reviewer facing an unbounded backlog degrades into a rubber stamp, which is a failure of the *same* human promotion gate the rest of this design leans on as its load-bearing safety control, not a throughput nuisance. Enabling cadence (the value) therefore erodes the gate (the safety); any future automated schedule must be conditioned on demonstrated gate-throughput headroom — the same gating Issue C already half-proposes for the confinement hook — and this compound path is graded in the risk matrix below.

**The promotion ladder's load-bearing gate sits one rung lower than the plan's stated guardrail covers.** The plan's guardrail — "the loop writes only `research/` and `ideas/`; promotion into rules/skills requires the human" — gates the rule-skill rung. The ladder itself, as stated in two places that do not fully agree with each other (`claude-port-plan.md` §3c: insight → MEMORY → rule-skill → cheatsheet; `memory-architecture.md` §6, which explicitly supersedes the port plan's ad-hoc memory position: trajectory note → short-term → active concept → `projections/active.md` → CLAUDE.md → rule-skill), has a MEMORY rung *below* the gated one, and under the memory-architecture design that rung's promotion (`short-term` → active concept) is automated once a fact has been seen in ≥ 2 trajectories, with the resulting "active concept" injected into every future session via a `CLAUDE.md` import. [minority: lane-2] The primary literature on self-referential data loops draws a sharp, evidenced line here rather than a blanket warning: training on generated data that *replaces* real data drives measurable distributional drift and loss of low-frequency information within a few generations[^6], but the direct rebuttal result shows that generated data *accumulating alongside* the original real data avoids that collapse across model sizes, architectures, and hyperparameters[^7]. That distinction — itself a training-time weight-drift finding, transferred here as inference about an in-context, human-gated corpus rather than an established fact about one — cuts *for* the plan's `research/`/`ideas/` design, which is exactly accumulate-only and git-tracked — but it cuts *against* the MEMORY rung as designed, because that rung's lifecycle prunes, deletes, decays, and regenerates the always-on `projections/active.md` view, which is a replace operation on the one surface every future session actually reads. [minority: lane-2] Two further primary results bound the hazard without over-claiming it: self-training on one's own unverified outputs is a documented source of confirmation bias with no inherent correction mechanism[^8] (measured in a pseudo-labeling setting, transferred here as inference rather than an established fact about MEMORY specifically); and knowledge-store poisoning research shows a small number of bad entries can dominate retrieval-augmented output even against a large corpus[^9] (measured for adversarial injection specifically — five malicious texts against millions of real ones — which this report does not claim transfers literally to spontaneous accretion, but which does establish that a store read back as evidence is fragile to a small number of wrong entries, however they got there). The repo's own `priors-are-poison.md` ruling (2026-07-19) reached a compatible conclusion independently, from inside the system rather than from the outside literature: cross-run priors read into a chair's context are "not neutral, it is likely HARMFUL," naming Goodhart's law, cross-topic confound, and salience as the mechanisms, and stating plainly that in-run feedback on the current question is legitimate while cross-run priors from other questions are not. The corrective this report can state precisely: the accumulate-only writes to `research/`+`ideas/` need no new gate; the MEMORY rung needs a stated write-discipline — never replace the real substrate, keep provenance, require corroboration from independent trajectories (not repetitions of the same error) before a fact becomes always-on context, and re-verify at the leaf on every read — most of which memory-architecture.md's own design already gestures at, but which the port plan's one-sentence guardrail does not name.

**Verification status, not design merit, decides #429 — and the status is now settled, not conditional.** The operator's binding process requirement is that recommendations resting on a falsifiable claim must be prototyped and tested, with an unrun-but-cheap check counted as an audit finding rather than an oversight. This is the same distinction the systems-engineering verification/validation standard draws formally — confirmation by objective evidence that a requirement is met (built right) versus confirmation that the built thing serves its intended use (the right thing built)[^10] — and it is why a sound design argument cannot substitute for a check that was never run. Self-improvement loops in the published literature are licensed the same way: a bootstrapping method that keeps only the outputs that pass a correctness filter converges, precisely because the filter is what stops the loop drifting on its own errors[^11]; for sleeper-service the filter is the human promotion gate plus the prototype-and-test discipline plus the write-confinement invariant, and none of the three has yet been exercised end-to-end. The Phase-4 row of the plan names exactly such a check: headless `claude -p "/self-improve"` produces a run dir plus an idea stub, touching only `research/`+`ideas/`. Because the artifact under test — `/self-improve` — does not exist in the tree, that check cannot have been run, and the honest verification state is not-testable-because-absent: a distinct and stronger statement than "tested-and-inconclusive" or "the design looks unsound," and one this report's own validation-loop discipline forbids collapsing into "the design looks fine." Separately, and directly: issue #429 was read at the leaf via the GitHub API. Its title is the ship-vs-withdraw question itself; its body names two honest exits (ship the first increment, or withdraw the plugin from the marketplace manifest and the bootstrap script's plugin list); and the issue owner's own comment takes it over choosing the first exit — "the ship the first increment exit, made concrete" — with implementation follow-ups intended as further tracked issues. Per this suite's own consent discipline, that is the human's call to make and he has made it; this report's job is therefore not to re-litigate ship-vs-withdraw but to state, as concretely and testably as the operator's brief asks, what "ship" must actually contain not to ship a husk that reads as done from the manifest while doing nothing — which is the recommendation set below.

## Analysis

Five convergent findings — four of them independently reached or corroborated by more than one research lane; the fifth, the MEMORY-rung under-gating finding, was reached by lane 2's primary-literature reading and corroborated by the repo's own `priors-are-poison.md` ruling (repo doctrine) rather than by a second independent research lane — the `show lines-of-inquiry` record attributes Q4 to lane 2 — joined by one folded-in single-lane correction (manifest honesty) for six tracked issues in all, each working from a different method (adversarial disconfirmation against the leaf; primary literature; direct repo/API audit), converge on a single answer to what "ship #429" must concretely mean. This enumeration is declared open: any further claim in this report that a finding was independently reached by more than one lane is subject to the same per-finding check against `show lines-of-inquiry`, not a blanket assertion. None of the four other design questions (topic selection, cadence, the memory rung, input-channel integrity) individually blocks shipping *if* each is met by its own named mitigation rather than by a single guardrail — recommendation 1's record-mediated reads for input-channel integrity, recommendation 2's written priority rule for topic selection, recommendation 4's manual-cadence default for cadence, and recommendation 5's write-discipline for the MEMORY rung; the risk matrix below grades all four on their own rows and credits exactly those mitigations — never write-confinement — for any of them. Write-confinement is a *separate*, fifth control — a blast-radius bound, not the soundness mitigation for any of the four: it governs *where* a misbehaving loop may write, never whether the picker is well-ordered, the cadence stable, the MEMORY rung un-poisoned, or the input channel un-starved (a badly-ordered picker still burns cycles inside the sandbox; an enabled schedule near ρ=1 still degrades the reviewer regardless of where its writes land). As a write-containment boundary it reaches the topic-selection and cadence writes — which land inside `research/`+`ideas/` — but not the MEMORY-rung writes, which escape it via the `CLAUDE.md` import and are covered by recommendation 5 rather than by confinement; input-channel integrity is a read it is structurally irrelevant to. It is that fifth control, scoped to what it bounds and not blanket-applied to all four, that bounds the loop's blast radius. That guarantee must not be over-read into a soundness guarantee: write-confinement bounds *where* a misbehaving loop may write, not whether the four deferred questions are *sound* — none of the four is made sound by confinement, and two of them its write boundary cannot even contain. Input-channel integrity is one — a selector reading a retired `research/*/friction.md` stays perfectly confined while silently selecting nothing (the plausible-zero starvation named above). The MEMORY rung is the other — its promoted active concept is injected into every future session via a `CLAUDE.md` import and regenerates the always-on `projections/active.md`, writes that land *outside* `research/`+`ideas/` and are therefore covered not by confinement but by recommendation 5's separate write-discipline, which is needed precisely because confinement does not reach that rung. And confinement is a write-side control only: it models nothing about the loop's *inputs*. An autonomous loop reads a friction/run-record corpus a contributor pull request or a prior run can seed, and during `/research` fetches external web sources untrusted by construction — either an avenue to steer what the debate proposes toward a standing rule that would bind every future session. The human promotion gate is the barrier on the *rule-skill* rung, and must there act as an *adversarial* review of input provenance, not merely a quality review. But it is not the *sole* barrier on the path from a seeded input to a standing rule, because it does not sit on every rung: under the memory-architecture design the MEMORY rung auto-promotes a fact seen in ≥2 trajectories into always-on context (via the `CLAUDE.md` import and `projections/active.md`) with no human gate at all — so a corpus-seeded fact that recurs across two cycles reaches every future session by an *ungated* second route, and the ≥2-trajectory bar does not distinguish two independent observations from one injection seen twice (the knowledge-store-poisoning result cited above shows how few wrong entries that takes). Recommendation 5's MEMORY write-discipline is what closes that route, and until it is in place the route is open; this untrusted-input × ungated-MEMORY-auto-promotion cross-term is graded in the risk matrix below, and the untrusted-input hypothesis itself is recorded as a pursued line of inquiry this round rather than asserted bare. Write-confinement does not address this input/threat axis at all, and — per the cadence cross-term graded below — a diverging review backlog degrades the rule-skill gate into a rubber stamp. Read in the reverse order, this is the reasoning: the design questions are real and each has a stated, cheap fix, but none of them is the reason an unattended loop would be dangerous to leave running; the reason is that the one safety property everything else depends on — bounded blast radius, and even that only for *local filesystem* writes (the loop's outward/API write surface — github MCP write verbs, git remote pushes, network egress — is a separate channel a path gate does not touch, narrowed and graded on its own row below) — is currently a sentence in a README, observed to hold on exactly one run, rather than a gate that fails closed. Fix that first, and the rest can ship as first-cut, honestly-labeled-as-first-cut recommendations rather than as blockers.

Recommended as tracked issues, each stated so a skeptic can re-run its acceptance criterion:

- **Friction and rulings read from the record, never from prose.** `/self-improve` must consume the friction event log and its operator projection, run records, telemetry, and `law/proposed/` rulings via the `motion` record — naming no `*.md` file as a data channel for any of the four. Acceptance: the shipped spec references no `research/*/friction.md`; with the friction writer stopped, the read errors or reports "not measured," never a silent zero indistinguishable from a clean board.
- **A written, auditable topic-priority rule before "pick one" runs unattended.** A one-line scoring rule (recurrence of distinct causes × blast-radius ÷ estimated fix-cost, ties broken by oldest-unaddressed) computed and logged before selection, with the chosen topic and its score recorded on the run's own record so a later run — or a human — can audit the ordering. Acceptance: a dry run prints the full ranked candidate list and each score component; the selection is the argmax or an explicitly logged human override.
- **Write-confinement as a tested, capability-gated mechanism, shipped with the loop rather than after it.** A `PreToolUse` gate on Write/Edit/MultiEdit/Bash that denies any loop-context write whose resolved path lands outside `research/`+`ideas/`. Acceptance: a seeded write to `plugins/` from loop context is denied; a write to `ideas/` succeeds; two failure classes must be handled separately, because they are not the same defect and a single "loud failure" criterion cannot cover both. (i) *Binary-absent-at-runtime*: the suite's own bootstrap convention deliberately fails **open** here — the existing `frank-exchange-of-views` `PreToolUse` hook, when its binary is missing, echoes one stderr line and exits 0 (leaf-confirmed against `hooks/hooks.json`), because an unguarded hook would crash-storm every tool call in the fresh-plugin-cache window before `doctor --fix` installs binaries. A confinement hook of the same class therefore cannot be made to fail loud against binary-absence without breaking that convention; the honest mitigation is not a louder hook but OS-level fail-closed enforcement — running each cycle under a real OS-enforced write boundary — a read-only bind-mount over everything but `research/`+`ideas/`, a dropped-privilege OS user holding no write grant elsewhere, or a container/seccomp jail — and NOT a bare git worktree, which changes no permissions at all (a worktree is a linked working directory under the same OS user, so it confers disposability — cheap rollback of the checkout — never write-exclusion). Such a boundary physically excludes everything outside `research/`+`ideas/`, so escape is impossible rather than hook-gated. (ii) *Harness-level non-registration*: a `PreToolUse` hook that never fires at all — which THIS run demonstrated live, the record tool's identity-binding hook reaching no seat — has no code path left to be loud, so no criterion running *inside* the hook can detect it; and a pre-launch canary checked once *before the first cycle* does not cover it either, because a scheduled loop runs many cycles across container recycles and the fresh-plugin-cache window recurs — a hook present at boot can be absent on a later cycle, a time-of-check/time-of-use gap the once-at-boot canary's coverage window does not close. The load-bearing control for *both* failure classes is therefore the same OS-level fail-closed enforcement named under (i): running each cycle under a real OS-enforced write boundary — a read-only bind-mount, a dropped-privilege user with no write grant outside `research/`+`ideas/`, or a container/seccomp jail; a git worktree is explicitly NOT such a boundary, since it shares the launching user's permissions and confers only disposability — so confinement holds whether or not any hook registers on that cycle. The pre-launch **liveness assertion** (a canary write from loop context, observed *denied*, before the loop starts) is retained only as a redundant pre-flight check, not the primary mitigation; if it is kept as a live gate it must re-arm before every cycle's first loop-context write, not once at boot, so its coverage window matches the failure's per-cycle recurrence. Only a binary that loads and then errors is in scope for the original "degrade to a loud failure" wording; the two classes above are graded as a blocker in the risk matrix below, not left as an unscored residual. And a path gate is a *local-filesystem* control only: it does not reach the loop's outward/API write surface — github MCP write verbs, git remote pushes, network egress — which this run's own Q13 read of #429 through the GitHub MCP proves is reachable from loop context. Because the loop's very deliverable (tracked issues) is itself an outward write, confinement on that axis cannot mean "deny all"; it means loop-context credentials scoped to withhold remote write/merge capability so every durable outward effect passes the human promotion gate rather than an autonomous push, with the residual outward-write channel graded on its own row below. That scope must name which github-MCP verbs survive it, since the deliverable is itself a remote write: the horn this report takes is that issue- and comment-creation are a *deliberately scoped exception* — the lowest-privilege outward write, a reviewable proposal that changes no code and merges nothing and is itself the object the human gate inspects — while push, branch-merge, and any write to code or release state are denied. That exception does not reopen the autonomous-durable-effect risk the row exists to close, because filing an issue mutates no codebase or release state the way a push or merge does. (The other horn — withhold issue-filing too, and a human files each issue from the loop's local draft — is an added value cost compounding the already-graded manual-cadence erosion, a heavier default this report does not adopt.) And credential-scoping is an *integrity* control on the write axis only; it does nothing for the *confidentiality* axis of the same egress, which the loop cannot deny wholesale because `/research` needs outbound fetches to function. A prompt-injected page fetched during `/research` can drive a crafted follow-on request that exfiltrates secrets or internal architecture over exactly that read-egress — the hazard this suite's own `agent-guardrails` skill already names as a standing rule (no secret, token, or architecture egress on external calls) — and write/merge denial does not reach it, because exfiltration needs only the read-egress the loop's core function requires. That axis needs its own control: an egress allowlist or DNS-filter restricting `/research` fetches to a vetted destination set, or, absent one in increment 1, an explicit accepted-residual; it is graded on its own row below.

"""
R4-5: which utilization rho actually backs the finite illustrative pair the report
labels 'at rho=1.00'? Method: M/M/1 steady state, L = rho/(1-rho); Little's law
L = lambda*W with lambda = rho*mu (Little's-law method cited c-c6032c0e). An M/M/1
queue at EXACTLY rho=1 is null-recurrent: L and W are infinite, so any FINITE pair
cannot sit at rho=1 -- it sits just below. Exact arithmetic via fractions.
"""
from fractions import Fraction as F

mu = F(3)  # promotions/week (documented illustrative service rate)

def rho_from_L(L):          # invert L = rho/(1-rho)  ->  rho = L/(L+1)
    return F(L) / (F(L) + 1)

def W_weeks(rho):           # time in system = 1/(mu - lambda), lambda = rho*mu
    lam = rho * mu
    return F(1) / (mu - lam)

for label, L in (("~14 items / ~5 wk  (report labels rho=0.93)", 14),
                 ("~749 items / ~250 wk (report labels rho=1.00)", 749)):
    rho = rho_from_L(L)
    W = W_weeks(rho)
    print(f"{label}")
    print(f"   exact rho = {L}/{L+1} = {float(rho):.6f}   (2dp -> {float(rho):.2f}, 3dp -> {float(rho):.3f})")
    print(f"   implied W = {float(W):.3f} wk   lambda = {float(rho*mu):.4f}/wk   mu-lambda = {float(mu-rho*mu):.4f}/wk")
    print(f"   is rho exactly 1.00? {rho == 1}")
    print()

#!/usr/bin/env python3
"""
Q3 — the sleeper-service promotion gate as an M/M/1 queue.

Arrivals  lambda : promotion-CANDIDATE-bearing autonomous runs per week.
                   Daily default cadence => 7 runs/week; yield p in [0,1] of runs
                   that actually produce a promotable candidate => lambda = 7*p.
Service   mu     : promotions a single maintainer can review-and-clear per week.
                   Each promotion = reading a full multi-round FEOV report + judging
                   a rule/skill change (Semantic Consent gate). Bounded by human hours.

Model note: the research/ and ideas/ writes are NOT gated (cheap, unbounded, fine).
The gated resource is promotion INTO rules/skills. That is the single-server queue.
rho = lambda/mu. rho >= 1 => backlog grows without bound => the gate becomes nominal
(the human stops reading). Little's law L = lambda*W ties backlog length to wait.
"""

def rho(lam, mu):
    return lam / mu

def mm1_metrics(lam, mu):
    # standard M/M/1 steady-state (valid only for rho<1)
    r = lam / mu
    if r >= 1:
        return r, float('inf'), float('inf')
    L = r / (1 - r)          # mean number in system (Little: L = lambda*W)
    W = 1 / (mu - lam)       # mean time in system (weeks)
    return r, L, W

print("=== rho = lambda/mu grid: daily cadence (7 runs/wk), varying yield p and human throughput mu ===")
print(f"{'yield p':>8} {'lambda(=7p)':>11} | " + " ".join(f"mu={m:<4}" for m in (1,2,3,5,7)))
for p in (1.0, 0.75, 0.5, 0.25, 0.1):
    lam = 7 * p
    row = []
    for mu in (1,2,3,5,7):
        r = rho(lam, mu)
        flag = "UNSTABLE" if r >= 1 else f"{r:.2f}"
        row.append(f"{flag:>7}")
    print(f"{p:>8} {lam:>11.2f} | " + " ".join(row))

print()
print("=== Stability frontier: max yield p s.t. rho<1, per human throughput mu (daily cadence) ===")
for mu in (1,2,3,5,7):
    # 7p < mu  => p < mu/7
    p_star = mu / 7.0
    print(f"  mu={mu}/wk  -> stable only if candidate-yield p < {min(p_star,1.0):.3f}"
          + ("  (always stable at daily cadence)" if p_star>=1 else ""))

print()
print("=== Backlog blow-up near the frontier (M/M/1, Little's law L=lambda*W), mu=3/wk ===")
mu = 3.0
for p in (0.1, 0.25, 0.40, 0.42, 0.428):
    lam = 7*p
    r, L, W = mm1_metrics(lam, mu)
    Ls = "inf" if L==float('inf') else f"{L:6.1f}"
    Ws = "inf" if W==float('inf') else f"{W:5.2f}"

#!/usr/bin/env python3
# R2-1: distinguish shape-robustness from magnitude-dependence in the cadence queue.
# Kingman's G/G/1 approximation for mean wait in queue:
#   Wq ~= ((Ca^2 + Cs^2) / 2) * (rho / (1 - rho)) * (1/mu)
# M/M/1 is the special case Ca^2 = Cs^2 = 1, giving factor 1 (exact M/M/1 Wq).
# Calendar-timed (deterministic) arrivals => Ca^2 -> 0; exponential-scale service => Cs^2 = 1,
# giving factor (0+1)/2 = 0.5. Claim under test: the ratio is EXACTLY 1/2 at EVERY rho
# (magnitude scales by a constant), while the rho/(1-rho) shape and its rho=1 divergence
# are preserved for any nonzero (Ca^2 + Cs^2) (shape is distribution-free).
from fractions import Fraction as F

def kingman_factor(ca2, cs2):
    return F(ca2 + cs2, 2)

def wq(rho, mu, ca2, cs2):
    # returns Fraction multiples of the base rho/(1-rho)/mu times the Kingman factor
    return kingman_factor(ca2, cs2) * F(rho) / (1 - F(rho)) / F(mu)

mu = 3  # promotions/week; cancels in the ratio, any positive value works
rows = []
ratios = set()
for rho in [F(1,2), F(7,10), F(9,10), F(93,100), F(99,100), F(999,1000)]:
    mm1 = wq(rho, mu, 1, 1)          # M/M/1: Ca^2=Cs^2=1
    cal = wq(rho, mu, 0, 1)          # calendar arrivals: Ca^2=0, Cs^2=1
    ratio = cal / mm1
    ratios.add(ratio)
