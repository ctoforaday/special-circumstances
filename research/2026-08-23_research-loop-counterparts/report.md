## TL;DR

Sleeper-service is FEOV's daily `/self-improve` cadence: a research debate (blue proposes, red audits, a bench judges termination) whose deliverable is an idea stub, gated on a human before anything reaches rules or skills. Measured against the external automated-research and self-improving-agent literature, no single mechanism FEOV uses is novel — constitution-bound critics, adversarial evaluators, execution-anchored verification, and late human gates each already exist somewhere in the corpus — but the *combination* (a fixed adversarial seat chartered to withhold a binary PASS, computation-gaps mechanically uncloseable on prose, every exchange a refusable record event, a human gate at the narrowest possible rung) is not attested co-located anywhere this run found. Measured against its own in-repo parallels, self-improve/dream/memory share one outer kernel (schedule → gather → consolidate → gated promotion → human ratification → git commit) but diverge irreducibly in how they consolidate, and — the sharper, code-level finding — only FEOV's gate is actually built: at the pinned commit, frank-exchange-of-views ships 336 Go files, its refusals enforced in a compiled write path (record.go's validate(), merge/close.go), while sleeper-service is a three-file scaffold and the dream loop / memory architecture ship no code at all. The sharpest caveat: red is a fixed, non-co-evolving evaluator, and the literature's own critique of stationary evaluators (Red Queen Gödel Machine) applies to sleeper-service's daily cadence without a built-in detector for it.

## The Catechism

**1. What are we trying to do?**
Sleeper-service runs a scheduled, largely-autonomous research loop — FEOV's adversarial blue/red/bench debate, invoked daily via `/self-improve` — that proposes how the suite's own rules, skills, and agents should evolve, writes only to `research/` and `ideas/`, and stops short of changing behavior until a human approves the promotion. It is one of three such loops in the repo: self-improve evolves the *rules*, the dream loop consolidates the *knowledge* base, and the memory architecture is the *substrate* both write to and read from.

**2. How is it handled today, and what does that cost us?**
Today, rule and skill evolution is manual: a person notices a recurring failure, writes it up, and edits a skill file by hand. That is accurate but unscheduled and effort-bound — it happens when someone has the time and the pattern is fresh, not on a cadence, and nothing forces a disconfirming pass before a fix ships. The cost is not that the manual process is wrong; it is that it does not run when no one is looking, and it carries no adversarial check by default. Elsewhere, comparable automated-research and self-improvement systems handle "how do we know the loop's output is any good" in one of four ways, none of which map cleanly onto a repo-scale rules corpus: self/same-family review (the generator grades its own output — AI-Scientist's simulated reviewer, Self-Refine's self-feedback), external ground-truth by execution (a benchmark or an `evaluate` function scores the change — Darwin Gödel Machine, AlphaEvolve, FunSearch), an external, co-evolving adversarial critic (an adversarial objective breeds reviewers equally stringent on AI and human work — Red Queen Gödel Machine, the class sitting closest to FEOV's own gate design), or no adversarial gate at all (deep-research products synthesize retrieved sources and hand off, with no execution and no adversary). None of the four is built for "audit whether a proposed change to an agent's own rules is a good idea," because none has an open-ended, prose-heavy, non-benchmarkable target the way a rules corpus is — the external-adversarial-critic class included: Red Queen Gödel Machine co-evolves its graders against a benchmarkable code-review signal, so even the closest analog is aimed at a machine-checkable objective a prose rules corpus does not supply — a difference in the KIND of target each was designed against, not an exhaustive-search result; the stronger claim, that no system anywhere occupies this niche, is the search-bounded one graded at item 4.

**3. What is new here, and why do we believe it works?**
Not any single mechanism — each piece already exists somewhere in the literature (see Technical foundations). What is new is the *bundle*, and specifically that FEOV mechanizes it rather than merely stating it: a critic (red) is a **fixed, separately-constituted seat chartered to withhold a binary PASS** rather than emit a training signal or a revisable critique; **computation-gaps are mechanically uncloseable on prose** — `mint` requires a stated `--check-kind`, and `merge close` refuses to close a `computation`-class gap without a matching `proof` event on the record; **every exchange is a refusable event** on an append-only log — a malformed `mint`, a `PASS` claimed over open gaps, a `close` with no verification triple, a dangling `supersedes` reference, are all rejected at the single write path (`Append`) rather than accepted and silently dropped; and the **human gate sits at the narrowest possible rung** — the loop can propose freely but cannot itself change behavior. We believe it works because a code audit of the pinned commit shows the record's refusals are implemented, not aspirational, and because the repo's own history (six-plus documented failures in `capture.go`) is a first-hand demonstration of what happens when the equivalent facts are *not* mediated this way — the exact failure the dream/memory design, as currently written, is positioned to repeat.

**4. The case against.**
Every honest objection, stated at full strength, including the risk-accepted residuals:
- **No single mechanism is novel, and a critic could reasonably say FEOV over-claims its originality if it is not careful.** Constitution-bound critique (Constitutional AI/RLAIF), adversarial evaluators calibrated specifically against AI-generated work (Red Queen Gödel Machine), whole-trajectory agentic judges with memory (Agent-as-a-Judge), and execution-anchored verification (Darwin Gödel Machine, AlphaEvolve, FunSearch) all already exist. The defensible claim is a specific, unattested-elsewhere *combination*, and that claim rests on absence of a counterexample across roughly two dozen searches across three independent lanes — weaker evidence than a positive attestation, so it is graded as such rather than asserted as proven uniqueness. The most on-point self-referential-improvement comparator, Boundless Socratic Learning, was leaf-checked this round — a position paper proposing recursive self-improvement via language games in a closed system, with no separately-constituted withholding critic, no refusable append-only record, and no computation-uncloseable-on-prose gate — so it is not a co-located counterexample, and the combination claim now rests on a specific check of that comparator class rather than on aggregate search breadth alone. *(likelihood × impact × complexity-to-mitigate: medium × medium × low)*.
- **Red is a fixed evaluator that does not co-evolve, and the strongest external critique of exactly this shape (RQGM) names sleeper-service's daily cadence as its target.** As `/self-improve` runs and blue learns which arguments pass red, Goodhart pressure accrues — blue could learn to pass red without the underlying work improving — and the current design has no mechanism that would detect this divergence. This is a **risk-accepted residual**, not a solved problem: the partial defenses (red's `memory: project` accumulating new gap patterns; the human promotion gate as a held-out check; execution proofs anchoring to reality) reduce but do not eliminate the exposure, and no periodic held-out audit exists to catch it — and any such audit is itself an LLM judge, so it must be independent in lineage, not merely fresh to the memory, and is bounded by the same judge-reliability limits Technical foundations §D documents; no lineage-independent reviewer is available to this same-vendor run. *(likelihood × impact × complexity-to-mitigate: medium × high × medium-high — the risk-accepted residual, and the highest-ranked objection in this list)*.
- **The self-preference-bias literature is a documented, unresolved failure mode of LLM-as-judge generally, and this run's own configuration sits inside it in a way that is not fully characterized.** Judge unreliability is empirically severe even across 21 judges from nine providers — judge rankings can shift by up to 14 positions across benchmarks, and high test–retest reliability has been shown to coexist with severe position bias in production-deployed judges. The pairing this run actually used — blue on `fable`, red on `sonnet` — is **same-vendor**: Claude Fable and Claude Sonnet are both Anthropic models, so this run buys no cross-vendor diversity at all. The most it can offer is *same-vendor, cross-model-size* diversity, and whether that reduces the shared-training-lineage bias the literature warns about — or buys nothing because the lineage is shared — is not settled by any source this run leaf-verified; it is carried forward as an open question, not resolved in FEOV's favor. *(likelihood × impact × complexity-to-mitigate: medium × medium × high)*.
- **Only one of the three in-repo loops is actually built.** At the pinned commit, sleeper-service is a three-file scaffold and the dream loop / memory architecture have zero implementation. Every convergence claim in this report about "three loops sharing a kernel" is, honestly, a claim about one running mechanism and two proposals; the comparison is real and useful, but it is not yet a comparison of three equally-real systems, and treating it as one before the code exists would be premature confidence. *(likelihood × impact × complexity-to-mitigate: realized × low-medium × low — true at this commit; the mitigation is to state it plainly, already done)*.
- **The memory/dream design, as currently written, is the shape FEOV's own audit history was rewritten to escape.** OKF v0.2's conformance rule forbids rejecting a document for missing optional fields, so the profile's lifecycle fields (`confidence`, `status`, `review_count`, `supersedes`) are recoverable by reading and never refused at write — a plausible-zero exposure the design's own §9.4 partially concedes (citing the OpenClaw diary's silent-loss failure) without yet proposing a write-time validator. This is a real, currently-open weakness in a design that has not shipped, which is the cheapest possible time to fix it and also a real cost: building that validator is additional scope nobody has committed to yet. *(likelihood × impact × complexity-to-mitigate: medium × medium × low-medium)*.
- **Cost and complexity are real, not hypothetical.** A daily research debate against the suite's own rules is not free: it is `fable`/`sonnet` API spend, a growing `research/` corpus that someone has to periodically prune or archive, and a promotion queue a human must actually review rather than rubber-stamp. If the human gate degrades into rubber-stamping (the same failure the FEOV record's `requirePassClosesAllGaps` refusal was built to prevent on red's side), sleeper-service's late-and-narrow gate provides no more safety than an unguarded self-improver — the safety property is enforced by a human paying attention, not by the architecture alone. *(likelihood × impact × complexity-to-mitigate: medium × medium-high × medium)*
- **The loop's INPUT trust is never modeled — the threat model covers only where output lands.** `/self-improve` runs a full FEOV research debate whose raw material is fetched external web sources, and that content flows into blue's idea stubs, which are proposals to change the suite's own rules and skills. A compromised or adversarial fetched source could mount two DISTINCT attacks here, needing different controls, and at the pinned commit the design names a control for neither. (a) **Behavioral injection on the proposal path**: fetched content hijacks blue's action, steering a proposal toward the very human gate the case-against already concedes may rubber-stamp; the control this calls for is input sanitization / sandboxing / instruction-provenance separating fetched data from instructions, and the write-scope guard (item 7) and human gate bound only where output may land, not whether the input is trusted — none of the former is implemented. (b) **Content/corroboration poisoning on the audit path**: FEOV's substrate fetches each external source once into the run cache and serves both sides the identical bytes (research-protocol's governing clause; the `fetch` verb caches at `<run>/cache/<sha256>` so every seat reads the same content — verified against the tool this round), and red's own constitution requires reading those exact cached bytes at the leaf to verify a citation, so a source crafted to make a false claim read as *corroborated* — hijacking no agent's behavior — can be aimed at red's audit path, degrading the single control the whole design leans on (a fixed adversarial seat chartered to withhold PASS); the control this calls for is different in kind — source reputation, cross-source corroboration, an independent truth check — and none of it is implemented either. The two are separate open exposures: for a headless daily `claude -p` loop whose target is the security-critical rules/skills surface, TWO controls are absent, not one, and a single input-provenance fix would close only (a). *(likelihood × impact × complexity-to-mitigate: low-medium × high × medium)*.
- **A third exposure the threat model never names: network egress.** The two vectors above concern input trust — what fetched content does to the loop — and the write-scope guard (item 7) bounds output landing, where the loop's writes go; neither covers what the headless loop transmits OUTWARD. `/self-improve` composes its research queries and source fetches ABOUT the suite's own rules, skills and agents by construction, which is precisely the content class this repo's own agent-guardrails skill forbids on external calls: "YOU MUST NOT send secrets, tokens, or internal architecture." A daily `claude -p` loop whose subject IS internal architecture is the archetypal case that prohibition names, and it transmits before and independently of the human promotion gate — a human declining to promote an idea does nothing to un-send a query that already left the process, so the one control the whole design leans on sits structurally downstream of this exposure. At the pinned commit no egress control (query/fetch sanitization, an allowlisted-destination fetch policy) bounds what leaves; the exposure is named here and left open, not claimed contained. *(likelihood × impact × complexity-to-mitigate: medium × medium-high × medium — the mitigation graded medium because a real egress policy trades against a research loop's need to fetch; the report-completeness fix of naming the axis is low, disputed accordingly)*.

**5. Of interest, or merely interesting?**
Of interest, conditionally. What it displaces is the status quo of manual, unscheduled rule-evolution — not a rival automated system: the automated-research systems this run surveyed all target closed, benchmarkable objectives, so auditing a change to an open-ended, prose-heavy, non-benchmarkable rules corpus is a categorically different target none is built for — a difference in the KIND of target each was designed against, definitional rather than a bare search result; and on the narrower question of whether some system nonetheless does exactly this, the same bounded-search caveat as item 4 applies (roughly two dozen searches across three lanes, weaker than a positive attestation). What it costs to find out is bounded: the FEOV substrate already exists and is exercised by every research run including this one, so sleeper-service's marginal build is the scheduling wrapper and the write-scope guard, not a new adversarial engine. What we would need to learn first, before calling it "of interest" without qualification, is whether the Goodhart residual (item 4) is contained at real cadence — that requires run history sleeper-service does not yet have (§ Open questions), which is exactly why this report stops at a positioning recommendation and defers the quantitative measurement to a later run.

**6. What changes if it works — and what happens if we simply don't do it?**
If it works: the suite gets a background process that proposes rule/skill evolution on a cadence no person has to remember to run, backed by the same adversarial-gate discipline this very research debate was produced under, with a human still the only one who can change behavior. If we don't do it: manual rule evolution continues exactly as it does today — which is not catastrophic (the suite has evolved this way already), but it means gaps surface only when someone happens to notice them, with no adversarial check unless a person chooses to invoke one, and no scheduled corpus of "things that went wrong" (friction) accumulating anywhere a future review can mine it systematically. Nothing bad is actively happening today by not building it; the cost of not doing it is a foregone systematic improvement, not an active harm — and that foregone-improvement framing is itself a verdict, not a hedge.

**7. What does it cost, and where would we stop?**
Cost: the scheduling wrapper, a write-scope guard restricting the loop to `research/`+`ideas/` (currently prose-only, per the case against), and ongoing `fable`/`sonnet` API spend per run at a daily default cadence — bounded, because the adversarial engine itself is already built and paid for by every FEOV research run. Where we would stop: if the write-scope guard cannot be mechanized (kept as README prose indefinitely) we should not let the loop run headless and unattended, because a prose guardrail binds nothing against a scheduled `claude -p` invocation; and if a held-out Goodhart check is not built within the first several cycles of real run history, the pass-rate trend should be treated as unverified rather than as evidence of quality, and promotions should require the same scrutiny as if no automated loop existed at all; and — the residual item 4 grades highest-impact-and-unmitigated — the loop should not run headless against external services until item 4 bullet 7's input-trust exposure carries at least one of its two named controls (input-provenance/instruction-separation on the proposal path, or source-corroboration on the audit path) AND the egress exposure (item 4's third threat-model bullet) carries a bounding control, since at the pinned commit the design names a control for none of the three, and naming exactly this kind of checkpoint is item 7's charter.

### A. What sleeper-service and FEOV are, as built and as designed

Sleeper-service is the autonomous-learning plugin: `/self-improve` runs at a daily default cadence, enumerates the suite's own rules/skills/agents/ideas/research, and **runs a full FEOV research debate** (`/research "how should X evolve?"`) as its consolidation step, producing an idea stub with alternatives; it writes only to `research/` and `ideas/`, and promotion into rules/skills requires the human (`plugins/sleeper-service/README.md`; `plans/claude-port-plan.md` §3c, §5; pinned `2ce929f`). At the pinned commit this plugin ships exactly three files — `.claude-plugin/plugin.json`, `README.md`, `bin/.gitkeep` — and its own README states "Status: scaffold only (Phase 0)" (`plugins/sleeper-service/README.md:9`, pinned `2ce929f`; leaf-verified by direct `git show` and by the reproducible proof below).

FEOV (frank-exchange-of-views) is, by contrast, a substantial Go program: 336 `.go` source and test files under `plugins/frank-exchange-of-views/tools/` at the same pinned commit (`git ls-tree`, leaf-counted; see the reproducible proof anchored in Analysis) — the running substrate this very research run writes through. Its record package implements `Append` as "the ONLY write path" for every seat-emitted event (mint, close, proof, cite, finding, verdict, motion, friction, line-of-inquiry), preceded by a `validate` gauntlet spanning roughly 530 lines that refuses, among other things: a `mint` missing `--check`, `--class`, `--check-kind`, `--likelihood`, `--impact`, or `--problem`; a `verdict` of `PASS` recorded while any gap is still open ("the 2026-07-20 rubber-stamp: PASS with 9 open gaps" is cited in-code as the incident that motivated the refusal); a `close` lacking the verification triple (`--verified-by/--verified-with/--verified-against`); and a dangling `supersedes`/`answers`/`successor` reference to a gap the board does not hold (`plugins/frank-exchange-of-views/tools/internal/record/record.go`, sampled at lines ~350–360, ~440–450, ~553–600, ~870–895; pinned `2ce929f`, leaf-read by this synthesis via `git show`). `check_kind` (document | computation | source) is itself a **required** field at `mint`, added specifically because "The 2026-08-05 smoke produced ZERO proofs across a full run… because NOTHING ASKED: all ten of red's acceptance checks were document probes" (same file, same range). A gap minted `check-kind computation` cannot later be closed on prose: `merge close` checks for a matching `proof` event on the record and refuses the closure otherwise (`plugins/frank-exchange-of-views/tools/internal/cli/merge/close.go` — `newClose()`'s `computationGapKind` + `record.ProofAnswers` guard — pinned `2ce929f`, leaf-verified line-for-line this round by this synthesis via `git show` and independently re-read by red at the same commit).

The repository's own capture/audit layer (`plugins/frank-exchange-of-views/tools/internal/capture/capture.go`, 1811 lines, pinned `2ce929f`) documents at least six historical instances of the exact failure this report's Technical foundations, below, argues the dream/memory design risks repeating: an audit that read a fact out of a markdown file or recovered it by regex/string-split, and returned a **plausible zero indistinguishable from a clean board** once the underlying artifact stopped being written the way the audit expected. Named instances: a line-count comparison against files that became rendered projections (silently SKIPping for months while reporting the newest runs as "pre-sharding" — leaf-verified by this synthesis at `capture.go:215–237`); a friction-parity check that split a string instead of joining on the `seat_id` field the record already held (reporting 5/5 failures on a run where every one was on record); a regex scan for `REFUTED|ABSENT` tokens over a prose column that became a 46-byte stub once grading became a closed enum (reporting PASS — 0 tokens — on every record-mode run); an attestation audit that split a pipe-delimited prose line back into fields the record already held ("reconciled nothing, in silence, for as long as the record tier has existed"); a CHANGELOG heading-count that missed a run carrying "a 6,847-byte CHANGELOG and exactly ONE revision event"; and a precedent-harvest reading free-text envelope arrays that reported "0 ruling(s)" indistinguishably from a run where the bench genuinely ruled nothing (the latter five per lane 3's leaf read, not independently re-verified line-for-line by this synthesis). Every one was fixed the same way: move the fact onto a refusable record field and read it in-process.

Red's own constitution frames the gate as **two-sided**, not merely withholding: "a CERTIFIED report: you win either by finding real defects or by issuing a PASS that survives scrutiny… an unearned FAIL is red losing, exactly as an unearned PASS is… Never-soft-pass has a twin: never-hard-fail," grounded in "13/13 FAIL across three runs" under an earlier endpoint-less constitution (`plugins/frank-exchange-of-views/agents/red-auditor.md`, pinned `2ce929f`, per lane 3's leaf read).

### B. The dream loop and the memory architecture, as designed

The memory-architecture proposal gives captured knowledge a versioned, git-native store: a directory of markdown files with YAML frontmatter, one "concept" per file, adopting the Open Knowledge Format (OKF) as the on-disk standard with a small profile (a fixed `type` vocabulary plus lifecycle fields) layered on top (`plans/memory-architecture.md`, pinned `2ce929f`). At the pinned commit this design ships as a proposal only — the document's own status line reads "Status: Proposal[^P1] (for discussion)" (`plans/memory-architecture.md:3`) — and a tree search for the primitives it names (`dream.js`, `memory-consolidator`, any OKF-profile file, a knowledge-store directory) returns nothing, reproducibly computed rather than asserted (see the proof anchored in Analysis, which also re-derives this search).

Its own profile states plainly that "only `type`… [is] strictly required (OKF compliance); the lifecycle fields (`status`, `confidence`, `last_seen`, `review_count`, `supersedes`, `provenance`) are our profile's additions… A file missing them is still a valid OKF concept — it is simply treated as a low-confidence candidate" (`plans/memory-architecture.md` §3.1, leaf-verified verbatim by this synthesis via `git show`). The dream loop's consolidation step is a single `memory-consolidator` agent performing overlap-dedup merges (expand-existing-before-append; set `supersedes`; bump `review_count`/`confidence`), with human review of the resulting git diff as the stated mitigation against silent loss — the design names the OpenClaw "Dream Diary" degrading to "a memory trace surfaced, but details were unavailable" explicitly as the cautionary tale it is trying to avoid (`plans/memory-architecture.md` §2, §7.5). The generated `active.md` projection (never hand-edited) does follow the facts-are-fields-preferred pattern of generating a derived carrier rather than guarding two hand-written copies; the underlying concept layer does not have an equivalent write-time check (`plans/memory-architecture.md` §4, §9.4).

The Open Knowledge Format itself, at v0.2, is explicit about its own permissiveness: producers "MAY include any additional keys[^1]," and consumers "MUST NOT reject documents with unrecognized fields" — the spec's conformance bar is "YAML parses" plus "`type` is non-empty," nothing more. The same v0.2 spec, independently of the memory-architecture proposal's use of it, defines an **Attested Computation** concept type: a sanctioned computation whose caller "MAY only supply *values*… MUST NOT author or edit the computation," run by an **executor** that returns a **receipt**, checked by a deterministic, no-LLM **attester** that "compar[es][^2]" the receipt against the sanctioned computation rather than exercising judgment. This is architecturally the same idea as FEOV's `proof:` mechanism — computed facts carry a re-runnable, mechanically-checkable receipt rather than prose — arrived at independently by a different standards effort.

## Analysis

**Q1 — is the externalized adversary a genuine differentiator?** Narrowed, not defeated. Every individual axis in FEOV's gate design already exists in the external corpus (Technical foundations §D). What none of the found systems attest together is the *combination*: a fixed seat, chartered to withhold rather than score-and-average, writing only through a refusable record, standing in front of a human-gated promotion. That is a real and defensible claim, but it rests on absence of a counterexample across roughly two dozen searches — weaker than a positive attestation, and — after this round leaf-checked Boundless Socratic Learning (arXiv 2411.16905), the most on-point self-referential-improvement comparator[^13], and found it is not a co-located counterexample to the four-trait combination — the claim rests on that specific check together with the search breadth, not on search count alone; it should be presented to red as a grounded-but-not-proven combination, not inflated into "FEOV invented adversarial verification."

**Q2 — one machine at three altitudes, or three separate machines?** Neither pole survives alone; the honest answer is both halves at once. The outer kernel (schedule → gather → consolidate → gated promotion → human ratification → commit) is real and shared, confirmed by a direct leaf read of both design docs (Technical foundations §C). The *consolidate* step is irreducibly three different mechanisms — an adversarial debate, a dedup-merge agent, a passive corroboration ladder — and collapsing them into one abstraction to satisfy symmetry would force each into a shape that fits none. The actionable, filable recommendation is therefore to extract the **kernel** (scheduling recipes, the promotion-ladder state machine, the human-gate-at-top-rung invariant, git-commit-per-pass) as shared infrastructure, and keep **consolidate** a pluggable strategy interface with three named implementations (`debate`, `dedup-merge`, `corroboration-count`). This recommendation is contingent, not validated-now: the overlap is read structurally off two design docs (one of which — the dream/memory loop — ships zero code at the pinned commit), and line-of-inquiry Q10 on this same record flags that a shared kernel could be "a forced abstraction that makes any of the three worse," naming a PROTOTYPE of the strategy-interface boundary against all three payloads (rules / consolidated knowledge / substrate concepts) as the step that would confirm the kernel is honestly shared. So the deliverable is to file the extraction with that Q10 prototype as its acceptance test, not to treat shareability-in-implementation as already settled.

**Q3 — is the record's mediation the load-bearing novelty?** Yes, and it survives at both the design-doc leaf and the code leaf — the latter making it a stronger and more concrete claim than a spec comparison alone could. OKF v0.2 is permissive by design (no rejection for missing optional fields); the memory profile's lifecycle fields are therefore recoverable-by-reading, never refused at write, which is precisely the "pattern standing in for a schema" shape facts-are-fields names, and the design's own §9.4 half-concedes it by naming the OpenClaw diary's silent-loss failure as a cautionary tale it has not yet fully answered. The FEOV record's `validate()` gauntlet is the opposite: a compiled refusal at the one write path, and the repository has already paid, in `capture.go`, for the lesson of what happens when the equivalent fact lives in prose instead — six-plus documented instances of an audit reading a plausible zero that looked exactly like a clean board. The facts-are-fields caveat must travel with this finding, though: the rule's own scope is narrow ("this is about bypassing a record you already have… where no record exists, creating one is a design decision with a cost, not an obligation"), so the correct, bounded recommendation is not "rebuild the memory store as feov-record" — it is **add a write-time validator that refuses a concept missing its structural identity fields** (`status`, `supersedes`), with the numeric promotion-ladder fields (`confidence`, `review_count`) gated at promotion rather than at write (see finding #2) — a small, cost-aware control matched to what facts-are-fields actually asks for. Separately, and independently valuable: OKF v0.2's Attested Computation concept type is convergent evolution with FEOV's `proof:` mechanism — a different standards effort arriving at "a computed fact needs a re-runnable, mechanically-checkable receipt, not prose" — which is external corroboration of the operator's own standing prototyping-and-testing requirement. The memory-architecture design currently pins to OKF v0.1 while v0.2 already ships first-class versions of several hand-rolled profile fields — provenance/`sources`, `verified`-derived trust tiers, and the `status`/`stale_after` lifecycle pair — so re-pinning and dropping *those specific* duplicates is a small, filable cleanup. One exemption keeps it scoped rather than blanket: v0.2 deliberately stores no numeric credibility score (its §5.1, leaf-verified this round against the cited spec: "it does not store a credibility score … credibility is inferred from the signals") and defines no `review_count`, so the memory profile's two numeric promotion-ladder gates — `confidence ≥ 0.7` and `review_count ≥ 2` (Technical foundations §C) — have no first-class v0.2 replacement and stay hand-rolled profile additions; dropping them under a blanket "lifecycle" sweep would delete the numeric promotion gate the mechanism runs on — the same `review_count ≥ 2` / `confidence ≥ 0.7` gate finding #2 checks at promotion rather than at write, which is why the two fields stay in the profile rather than being dropped.

**Q4 — is gate placement the distinctive risk-posture axis?** Yes, with a code-level qualification the design-doc reading alone cannot see. The census (Technical foundations §D) orders cleanly by gate position: no gate in the loop (DGM architecturally, AlphaEvolve, FunSearch), gate at the query (deep-research products, which scope the question up front and do not appear to persist state — unconfirmed at leaf this run), and gate uniquely late and narrow (sleeper-service/FEOV, converging with dream and memory on "propose freely, human ratifies behavior change"). The qualification: the three in-repo loops converge on gate *position* only as a matter of *design intent*. A code audit of the pinned commit shows only FEOV's gate is *mechanized* — the `verdict`/`PASS` refusal, the computation-close refusal, and `capture.go`'s post-hoc audits are compiled Go — while the sleeper-service/dream/memory promotion guardrail ("writes only `research/`+`ideas/`; promotion requires the human") lives in README and design-doc prose with no implemented write-scope enforcement at this commit. The three loops converge on gate *position* and diverge on gate *enforcement altitude*; making them genuinely parallel means giving the sleeper/dream/memory promotion gate the same mechanization FEOV's record already has — a compiled write-scope guard, not a prose guardrail a headless `claude -p` loop can silently overrun.

**Q5 — is execution-anchored proof the targeted countermeasure, or already standard?** Both, in different task classes. Execution-as-ground-truth is the established norm for closed, machine-checkable objectives (DGM's benchmarks, AlphaEvolve's and FunSearch's evaluator functions) — table stakes there, and the theoretical ancestor (Gödel Machine, 2003) already gated self-rewrite on proof, so FEOV's `proof:` anchor is a pragmatic weakening of a two-decade-old idea, not a novel one. What is largely absent from *open-ended research-report generation* — where AI-Scientist and deep-research products fall back to LLM review or source-corroboration — is exactly this discipline, and the documented failure it targets is real: NeurIPS-class venues have reported confirmed hallucinated citations even under peer review, and AI-Scientist-class output exhibits faked experimental results and mathematical errors in the wider MLR-Bench failure taxonomy (both reported by the lanes; not independently leaf-verified in this synthesis pass, so graded accordingly). FEOV's transplant of execution-anchored verification into the open-ended-research task class is the honest, narrower contribution, and the code confirms it is mechanized rather than aspirational: `mint` requires a stated `--check-kind`, added specifically because an earlier run produced zero proofs when nothing required declaring whether prose could settle a check, and `merge close` refuses to close a computation-class gap without a matching proof event.

**Build-state asymmetry (a finding this synthesis adds to the round-0 hypotheses).** Every comparison above compares FEOV as a running mechanism against sleeper-service, the dream loop, and the memory architecture as designs — and, for two of those three, designs with zero implementation. At the pinned commit, frank-exchange-of-views ships 336 Go source/test files; sleeper-service ships three files and is self-labeled Phase-0 scaffold; the dream loop and memory architecture ship no code at all[^P2], and the design doc self-labels "Proposal." This is not a reason to discount the comparison — it is a reason to state, once and plainly, what kind of comparison it is: a positioning report can honestly say the three loops share machinery *by design*, but cannot yet say they share it *in practice*, and the cheapest time to fix the memory design's mediation weakness (Q3) is now, before the consolidator exists, not after.

**A residual risk this run surfaces and does not resolve.** Red is a fixed, constitution-bound evaluator; it does not co-evolve with blue the way self-improvement search "generally assume[s] a stationary evaluation criterion: a fixed verifier, benchmark, or labeled dataset that remains valid as the agent improves," which RQGM argues[^14] "ignores a central feature of evolution." Sleeper-service's daily cadence runs exactly against that stationary bar. The partial mitigations already in the design (red's accumulating gap-pattern memory, the human promotion gate, execution-anchored proofs) reduce but do not eliminate the exposure that blue could learn to pass red without the underlying work getting better — and nothing in the current design measures that divergence directly. This is filed as a risk-accepted residual (Catechism, item 4) and as a concrete recommendation: a periodic held-out audit using a reviewer that has not seen the accumulating gap-pattern memory, comparing its verdicts against red's own trajectory once sleeper-service has real run history to measure. Two limits this report proves elsewhere bound that detector and must travel with the recommendation, because the held-out reviewer is itself an LLM judge: (i) it inherits the judge-reliability fragility Technical foundations §D documents — rankings shifting by up to 14 positions, severe position bias coexisting with high test–retest reliability — so a divergence it reports could be judge noise and an agreement could be shared bias, not Goodhart signal; and (ii) "has not seen the memory" buys freshness, not lineage independence — a reviewer drawn from the same vendor inherits the same-vendor shared-lineage exposure item 4 concedes is unsettled. The honest form is a reviewer independent in lineage, not only in memory; at this run none is available (both seats are Anthropic), so the recommendation is provisional on finding one.

**Filable convergence/divergence findings, concrete enough to track as issues:**
1. Extract the shared outer kernel (schedule, gather, gated-promotion state machine, human-gate-at-top-rung, git-commit-per-pass) as reusable infrastructure across self-improve/dream/memory; keep `consolidate` a named, pluggable strategy per loop (`debate` / `dedup-merge` / `corroboration-count`) rather than forcing one abstraction over all three — contingent on a prototype (per line-of-inquiry Q10) confirming the shared kernel degrades none of the three loops, since the overlap is read off two design docs, one shipping no code; the prototype is this finding's acceptance test, not a step to skip.
2. Give the OKF memory profile a write-time validator that refuses a concept missing its structural identity fields (`status`, `supersedes`), before the consolidator exists — the cheapest possible point to add it. The two numeric promotion-ladder fields (`confidence`, `review_count`) are deliberately NOT required at write: Technical foundations B's intake model treats a file missing them as a valid, low-confidence OKF candidate, and the promotion ladder (Technical foundations C) is what populates and gates them (`review_count ≥ 2`, `confidence ≥ 0.7`), so the validator checks those two at the promotion gate, not at creation — reconciling with finding #3's exemption rather than forbidding the nascent-candidate intake the ladder starts from.
3. Re-pin the memory-architecture profile to OKF v0.2 and drop only the hand-rolled fields it genuinely duplicates — provenance/`sources`, `verified`-derived trust tiers, and the `status`/`stale_after` lifecycle pair — now that upstream ships those first-class. Explicitly EXEMPT the two numeric promotion-ladder fields `confidence` and `review_count`: OKF v0.2 stores no numeric credibility score and defines no `review_count` (§5.1, leaf-verified), so those stay hand-rolled profile additions — consistent with finding #2's promotion-gate check, not dropped by it.
4. Adopt OKF v0.2's Attested Computation concept type for any quantitative/computed memory concept, reusing its executor/receipt/attester shape rather than inventing a parallel one.
5. Mechanize the sleeper-service/dream/memory write-scope-and-promotion guardrail as a compiled hook that refuses out-of-scope writes, matching FEOV's enforced gate, rather than leaving it as README/design-doc prose a headless loop can silently overrun.
6. Reuse FEOV's friction-record mediation pattern for the dream loop's knowledge substrate, since self-improve's gather step already inherits it and the two sleeper-service loops should not carry two different-strength persistence disciplines from birth.
7. Build a periodic held-out audit against red's fixed-evaluator Goodhart exposure once sleeper-service has real cycle history to measure against — using a reviewer independent in training lineage, not merely fresh to the accumulating gap-pattern memory, and reading its verdicts under the judge-reliability bounds Technical foundations §D documents; if no lineage-independent reviewer is available, the audit is provisional on finding one rather than a clean drop-in.
